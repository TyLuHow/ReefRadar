## 0. What's already decided / already built (don't re-derive)

- **Live backend** (`.planning/codebase/STACK.md`, `INTEGRATIONS.md`): Python 3.11 zip-deployed Lambdas (`router`, `preprocessor`, `classifier`) + a Python 3.12 **container-image** Lambda (`inference`) running `tensorflow-cpu>=2.18.0`, loading the SurfPerch SavedModel via `kagglehub.model_download()` + `tf.saved_model.load()`. S3 buckets `reefradar-2477-audio`, `reefradar-2477-embeddings`; DynamoDB `reefradar-2477-metadata`; account `781978598306`, `us-east-1`.
- **Prior-art transfer scripts already in the repo** (`scripts/marrs_cloud_transfer.py`, `infrastructure/ec2_transfer_template.yaml`): a **sampling-only** pipeline (200 files/site, ~16 GB, <$5) that downloads each site ZIP whole to a temp file on a `t3.small` Spot instance, then uploads a subset to S3. This is the right shape for the design (streaming download → S3 PUT, self-terminating Spot instance, CloudWatch billing alarm, lifecycle policy) but **does not scale to the full ~1 TB / 542k-file ingestion** Q3 calls for — see §1.
- **Data-model audit** (`.planning/audit/DATA-MODEL.md`): confirms the numbers this document is sized against — MARRS 542,187 one-minute files (~1.04 TB uncompressed, ~566 GB zipped across 45 site ZIPs), sonotype detections ~66 GB across 5 country ZIPs, Hurricane Irma (Dryad, CC0, 48 kHz, 2 sites), plus the integrity finding that the deployed classifier was very likely trained partly on synthetic audio and must be retrained clean (F2/F3).
- **MARRS filename timezone is unverified** (`PROJECT.md`, `DATA-MODEL.md §3.1`) — HydroMoth/AudioMoth firmware defaults to UTC; this must be confirmed against `manifest.csv`/device logs before any diel (hour-of-day) aggregate is computed, or every "dawn chorus" / "midday" claim in the product is wrong by up to the local UTC offset.

| Library | Version | Purpose | When to Use |

Proven at huge scale between AWS-compatible endpoints, but irrelevant here; don't spend time evaluating it further. `[WEB]` |
| **S3 Intelligent-Tiering / lifecycle rules** | n/a | Cost control on the raw-audio bucket | Raw MARRS WAVs are ingested once and mostly read sequentially by the batch embedding job, then rarely touched again except for on-demand spectrogram/clip serving. ## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|--------------|-------------|--------------------------|
| **AWS Batch (Spot EC2/Fargate, GPU-capable)** for both transfer and embedding | **SageMaker Processing jobs** | Use SageMaker Processing if you want a managed, auto-scaling, built-in-metrics path and don't mind paying the SageMaker markup over raw EC2/Fargate (observed in research as roughly 2–4x for equivalent compute depending on instance family). For a one-off/milestone-driven batch job run a handful of times, AWS Batch is cheaper and keeps you on infra you already understand (Lambda/EC2), with no new IAM/service surface to learn. Revisit SageMaker if the retrain cadence becomes continuous/scheduled. `[WEB]` |
| **AWS Batch** for orchestration | **Plain EC2 Spot + shell script** (the pattern in `ec2_transfer_template.yaml` today) | Fine for the first exploratory/sampled runs (as today), but at full 1 TB / 6.5M-window scale you want retry-per-shard and parallelism without hand-rolling a fleet — that's exactly what Batch array jobs give you for free. Keep the existing CloudFormation template as the Phase-0 sampling tool; introduce Batch for the Phase-1 full ingestion. |
| **LanceDB** for window-level similarity search | **FAISS** (e.g. `faiss-cpu`, IVF-PQ index built offline, loaded read-only into a container/Lambda) | Use FAISS if you decide the window-level similarity feature is a single, infrequently-rebuilt, read-only index served from one process with no need for S3-native storage, SQL filtering by site/date, or incremental updates. FAISS is lighter-weight to reason about for that narrow use case. Use LanceDB if you want metadata-filtered search (e.g., "nearest windows at healthy sites in Indonesia only") or want the vector store itself to live durably on S3 without a bespoke build/upload step. |
| **LanceDB/FAISS ANN index** for 6.5M window embeddings | **Brute-force NumPy cosine** (current approach, kept for the 48 site-mean vectors) | Brute force remains correct and fast enough for the *existing* 48-site reference set (276 KB) — do not change that code path. Only the new 6.5M-window table needs an index; even there, if the window-level similarity feature turns out to be "nearest window within the same site" or similarly pre-filtered, a per-site brute-force NumPy search (tens of thousands of rows per site) may still beat the complexity of standing up ANN. Decide based on the actual query pattern the Listening Bench needs, not in the abstract. |
| **Static versioned Parquet/JSON on CDN** for precomputed aggregates | **DuckDB-WASM in the browser over Parquet on S3** | Matches TECH-LANDSCAPE.md §7's existing "No — revisit only if you load thousands of per-segment rows from many recordings" verdict, now revisited: even with ~6.5M window rows upstream, the **frontend never needs row-level access** — it needs a handful of fixed aggregate shapes (per site × hour-of-day × date; per-detection-class counts; PCA/UMAP coordinates for 48–thousands of points; spectrogram tiles). Precompute those shapes once per dataset-contract version with DuckDB (offline, not WASM) and ship them as static files. Reconsider DuckDB-WASM only if a later milestone wants genuinely ad hoc, unanticipated slicing of row-level data in the browser — not needed for the aggregates this milestone specifies. |
| **Static files + tiny Lambda query endpoints for the few parameterized cases** (e.g., "detections in this date range for this site") | **DuckDB-WASM** or **a full query API** | A small number of static files per site/metric covers "per site × hour-of-day" and "per site × date" cleanly (both are bounded, enumerable keys). For genuinely open-ended range queries (arbitrary date range, arbitrary site set) that don't partition cleanly into static files, a thin Lambda reading a pre-partitioned Parquet-on-S3 dataset (via `pyarrow.dataset` with predicate pushdown, or DuckDB running inside the Lambda, not DuckDB-WASM) is cheaper to build than standing up a DuckDB-WASM client runtime and keeps the "no spatial/query database" discipline TECH-LANDSCAPE.md already established. |
| **Plain versioned S3 artifacts + a `manifest.json`** (recommended default for a one-operator, milestone-cadence retrain) | **DVC** | Adopt DVC if the data/model versioning needs to live inside git history with diffable pointer files and you want `dvc repro` pipeline reproducibility across contributors. Worth it once more than one person touches the ML pipeline, or once there are more than a handful of dataset/model version bumps to track. For this milestone (one retrain, behind one versioned data contract per `PROJECT.md`'s "Data & Model track runs parallel... behind a versioned data contract" decision), a `models/v{n}/model_config.json` + `models/v{n}/model.npz` + a top-level `MODEL_CARD.md` on S3, mirroring the existing `model_config.json`/`.npz` convention already in the repo, is simpler and has zero new tooling to learn. |
| **Plain versioned S3 artifacts** (same, for experiment tracking) | **MLflow** | Adopt MLflow if you expect to run many retrain variants (different embedding model, different hyperparameters, different site splits) and want a comparison UI/registry. ## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| **Full-ZIP-to-temp-file download for the full-scale ingestion** (i.e., scaling up `marrs_cloud_transfer.py`'s current pattern unchanged) | Works for the 16 GB sampled transfer; at full scale, multiple 10–50 GB ZIPs serialized through local temp storage means large EBS volumes, slow restart-from-scratch on failure, and no parallelism across files within a ZIP. | Stream individual WAV members directly from Figshare to S3 via `remotezip` + multipart upload, parallelized across files (and across sites, via Batch array jobs) — no full ZIP ever touches disk. |
| **AWS DataSync for the Figshare/Dryad transfer** | No HTTPS/generic-web source connector exists for DataSync; it only speaks to NFS/SMB/S3/EFS/FSx/S3-compatible endpoints. | Custom streaming transfer (AWS Batch + `remotezip`/`requests` + boto3 multipart), as above. |
| **SageMaker generally for this milestone** (training *and* the already-removed SageMaker inference path) | `.planning/codebase/STACK.md` confirms SageMaker inference was already explicitly deleted from this account (2026-02-20) in favor of the Lambda container; re-introducing SageMaker (Processing or Training) adds a second ML-ops surface, a markup over raw compute, and contradicts the project's own prior simplification. | AWS Batch (CPU for transfer/indices, GPU-capable compute environment for the embedding pass) feeding the same Lambda-container deploy pattern already in place. |
| **GPU Fargate for the embedding job** | Fargate has no GPU support (hard platform limit — 32 vCPU / 244 GiB max, no GPU attach). | AWS Batch with an EC2 Spot GPU compute environment (G4dn/G5), or stay CPU-only on Fargate Spot if the cost/throughput math favors many cheap CPU workers over fewer GPU workers for a 5-second-window EfficientNet-family embedding model — size both before committing (§ below). |
| **`scipy.signal.resample` (FFT-based) for any downsampling step** | Not anti-aliased; aliases high-frequency content into the passband exactly like the bug already found in the deployed preprocessor (DATA-MODEL.md F8c). | `scipy.signal.resample_poly` (polyphase, anti-aliased, integer-ratio) for every new batch/offline resampling path; fix the live preprocessor's `resample_linear` to match in a follow-on phase so train/serve resampling is consistent. |
| **WAF directly on the HTTP API (API Gateway v2)** | Not supported — HTTP APIs cannot have a WAF Web ACL attached directly, only REST APIs, ALBs, or CloudFront can. | Put CloudFront in front of the HTTP API and attach WAF there, or rely on API Gateway's native throttling alone if CloudFront is out of scope for this milestone. |
| **DuckDB-WASM as the default serving mechanism for precomputed aggregates** | Adds a multi-MB WASM runtime to the client for query shapes that are few, fixed, and enumerable (per-site × hour-of-day; per-site × date) — the exact over-engineering TECH-LANDSCAPE.md already warns against, now re-confirmed even with the larger upstream dataset, because the *frontend-facing* aggregate volume stays small regardless of how many raw windows feed it. | Static versioned Parquet/JSON on CDN for the fixed shapes; a small Lambda-over-Parquet-on-S3 query endpoint only for the few genuinely parameterized queries that don't partition into static files. |
| **A new general-purpose relational/spatial database (Postgres/PostGIS/Aurora) for embeddings or detections** | Not warranted at this row count (~6.5M embedding rows, a few million detection rows) — Parquet-on-S3 plus (optionally) LanceDB already covers both the analytical-aggregate and similarity-search needs without a persistent, always-on database to operate, patch, and pay for idle capacity on. | Partitioned Parquet on S3 + LanceDB (or brute-force per-site NumPy) for the one feature that genuinely needs nearest-neighbor search. |
| **Committing SurfPerch/Perch weights or large dataset files to git** | The repo's `.gitignore` already excludes `data/`, `models/*.npz`, `models/*.json` for this reason (`.planning/codebase/INTEGRATIONS.md`); multi-hundred-MB model weights and GB-scale data have no place in git history. | S3 for all weights/data/embeddings, versioned by key prefix (`models/v{n}/...`) with a manifest, consistent with the existing convention. |

## Stack Patterns by Variant

**If the embedding job is CPU-bound and throughput-tolerant (likely true for a 5s-window EfficientNet-family model at ~6.5M windows):**
- Use **AWS Batch with Fargate Spot** (or EC2 Spot, non-GPU instance families), high parallelism via array jobs (one job per site-shard or per N-thousand-window shard).
- Because: no GPU driver/container complexity, Fargate's per-task billing granularity is easy to cost-model, and Spot savings (60–90%) apply equally. Benchmark actual throughput (windows/sec/vCPU) on a small shard **before** committing to the full job — this determines whether CPU-only is actually cheaper than GPU once wall-clock is factored in.

**If a cost/throughput pilot shows GPU materially cuts total $ (fewer, faster workers vs many slow CPU workers):**
- Use **AWS Batch with an EC2 Spot GPU compute environment** (G4dn is the cost-effective default for inference-only workloads; G5 if the model is large enough to benefit from newer GPU memory bandwidth).
- Because: TensorFlow SavedModel inference at this volume (6.5M 5-second windows ≈ 9,000 h of audio) can plausibly be GPU-throughput-bound even for a relatively small EfficientNet-family backbone; always run the pilot (§ below) rather than assuming either direction.

**If you evaluate Perch 2.0 alongside SurfPerch (Q2 requires this):**
- Run **both embedding passes as separate, identically-shaped Batch jobs** writing to separate S3/Parquet prefixes (`embeddings/surfperch/v1/...`, `embeddings/perch2/v1/...`), then compare downstream classifier performance (leave-one-site-out balanced accuracy + CI) per embedding model before picking one for production.
- Because: this keeps the evaluation honest (same CV splits, same classifier architecture, only the embedding model differs) and gives you the model-card-ready comparison table Q2 calls for.

**If the retrain needs to happen more than once this milestone (iterating on class definitions, synthetic-data removal, site splits):**
- Use the lightweight **versioned-S3 + manifest.json** convention for every run, even if you don't adopt MLflow/DVC — append one row per run to a flat results table (CSV or JSON) so "which run is deployed" and "what was its leave-one-site-out CI" are always answerable from one file.
- Because: reproducibility here is a correctness requirement from `PROJECT.md` ("Truth & reproducibility" / "deployed model verified"), not a nice-to-have — a single source of truth for "this is the model in prod and here's its evaluation" is the minimum bar, independent of tooling choice.

## Reproducibility & evaluation recommendations (Q2 detail)

1. **Grouped, not random, CV.** Use `sklearn.model_selection.LeaveOneGroupOut` or `GroupKFold` with `groups=site_id` (and consider `groups=country` as a second, stricter evaluation) — this directly fixes DATA-MODEL.md F3 (current split leaks site identity, test n≈10–21).
2. **Calibrate, don't multiply.** Replace the deployed region-based 0.6/0.7 probability multiplier (F7) with `CalibratedClassifierCV` (sigmoid for small-n, isotonic if you have enough calibration data) fit **per CV fold**, so reported probabilities stay honest (summing to 1, and actually meaning what a probability means).
3. **Bootstrap CIs**, not a single point accuracy. With a small number of held-out sites/groups, resample (bootstrap) the per-window predictions within each held-out group many times to get a confidence interval on balanced accuracy / F1 — report this interval in the model card, not a bare percentage, directly addressing DATA-MODEL.md's "a 95% CI on 9/10 is about 55–100%" critique.
4. **Remove synthetic training rows entirely** before any of the above — `scripts/add_restored_mid_and_retrain.py`'s synthetic `restored_mid` rows (DATA-MODEL.md F2) must not appear in the retrain's training or evaluation sets, by class removal or genuine real-audio replacement, consistent with `PROJECT.md`'s "all synthetic audio and synthetic-trained classes removed."
5. **Evaluate SurfPerch vs Perch 2.0 under the identical CV scheme and identical classifier**, so the comparison isolates the embedding model as the only variable — this is the evidence Q2's model card needs to justify whichever embedding model is deployed.
6. **Model card + versioned contract**: publish a `MODEL_CARD.md` alongside the versioned model artifact (`models/v{n}/`) stating: training sites/sources used, CV scheme, balanced accuracy + CI per class, known confounds carried over from the data (site-leakage risk even under grouped CV given only ~5–10 real sites per class, region confound, diel confound), and the embedding model + version used. This satisfies `PROJECT.md`'s "published model card; versioned dataset/model contract."
