<objective>
Close the gap that blocks plan 02-12: a real browser cannot read the live contract. The contract CDN (distribution E1SD3UZ4FZ1GWL, d7dr1fzple2sg.cloudfront.net) uses the AWS managed Managed-SimpleCORS response headers policy, which adds Access-Control-Allow-Origin only to *simple* CORS requests. Chrome always adds non-safelisted headers to a fetch (`Priority: u=1, i`; `Cache-Control`/`Pragma: no-cache` on a hard reload), so CloudFront omits the header on every real browser request and the browser blocks the response ("blocked by CORS policy"), on cache hits and misses alike. `scripts/verify_contract_live.py` missed it because it sends only an Origin header.

Fix it as the owner decided (2026-10-01): replace the response headers policy with a custom wildcard CORS policy attached through the existing idempotent setup script, and make the live verifier browser-realistic so this class of defect can never pass verification again. The change also delivers the CONTEXT promise in "Hosting and publishing": the contract "is served to the browser (CORS for the dashboard origins and localhost)". CloudFront settings are Claude's discretion per CONTEXT; the choices below are recorded with their rationale.

Purpose: CONTRACT-01 ("the only source of reference data for the web app") is not true in a real browser until the CDN answers browser requests with CORS headers. CONTRACT-05 is protected by keeping the new live browser check out of the mocked e2e project, so UI work still runs only against committed fixtures.

## Design decisions (CloudFront settings are Claude's discretion per 02-CONTEXT.md)

| Setting | Choice | Rationale |
|---|---|---|
| Response headers policy | New custom policy `reefradar-2477-contract-cors`: `CorsConfig` AccessControlAllowOrigins `["*"]`, AccessControlAllowHeaders `["*"]`, AccessControlAllowMethods `["GET","HEAD","OPTIONS"]`, AccessControlAllowCredentials `false`, AccessControlMaxAgeSec `600`, OriginOverride `true`; no AccessControlExposeHeaders, no security/custom/remove/server-timing sections | Managed-SimpleCORS only answers *simple* CORS requests (AWS docs, "Use managed response headers policies": "adds the header Access-Control-Allow-Origin: * to all responses for simple CORS requests"). AllowHeaders `*` covers every browser-added header (AWS docs: `*` matches all headers except Authorization, which the app never sends). Wildcard origin is kept from 02-02: public, open-licensed, immutable data fetched with `credentials: 'omit'` (`dashboard-next/src/features/contract/client.ts`), and `*.vercel.app` preview hosts cannot be listed. No expose headers: the contract module reads bodies only, and Content-Type, Content-Length and Cache-Control are already CORS-safelisted response headers. OriginOverride true keeps the policy the single CORS authority even if a bucket CORS rule ever appears. The managed CORS-With-Preflight policy (5cc3b908-e619-4b99-88e5-2cf7f45965bd) was not chosen because it advertises DELETE/PATCH/POST/PUT. |
| Distribution AllowedMethods | `GET, HEAD, OPTIONS`; CachedMethods stay `GET, HEAD` | A method outside AllowedMethods is refused by CloudFront with 403 before any CORS handling, so a preflight cannot succeed with GET/HEAD only. GET/HEAD/OPTIONS is the narrowest allowed combination that admits OPTIONS and adds no write method; the bucket policy grants only `s3:GetObject`, so an OPTIONS that reaches S3 changes nothing. OPTIONS is not cached because the CachingOptimized cache key has no Origin or Access-Control-Request-* headers (AWS docs, "Configure CloudFront to respect CORS settings": caching OPTIONS requires forwarding those headers), so a cached preflight could be served for a different request. |
| Invalidation | None | AWS docs, "Add or remove HTTP headers in CloudFront responses with a policy": "CloudFront modifies the headers in the responses that it serves from the cache and the ones that it forwards from the origin." The policy applies at response time; cached objects are correct as they are. |
| Preflight handling | [ASSUMED, resolved live] | AWS documents which headers a preflight response carries but not whether CloudFront answers an OPTIONS at the edge or relays the S3 origin's answer (S3 has no bucket CORS and receives no Origin header under CachingOptimized). Real browsers do not preflight the contract module's requests: a plain GET with no author-set headers, where Priority and the cache headers are added by the browser after the CORS check. Task 3 therefore has a decision gate if only the preflight probes fail. |
| Actual-request evaluation | [ASSUMED, resolved live] | That CloudFront adds Access-Control-Allow-Origin to a non-simple GET once every request header is covered by AllowHeaders `*`. Task 3 rolls back and stops if the browser-profile GET probes still fail. |
